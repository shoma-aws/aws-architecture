# 概要
CloudWatch AlarmをトリガーとしてLambdaを自動実行し、CloudWatch Logs・CloudWatch Metrics・CloudTrailから取得した情報を統合してAmazon Bedrock（Claude）へ送信することで、インフラの状態や障害の原因をAIが自動分析するシステムを構築しました。<br>
ログ・メトリクス・操作履歴を横断的に分析し、障害発生時の初動対応を支援することを目的としています。

# 作成理由
業務の中で、障害が発生した際にはまずログやメトリクスを確認し原因調査を行いますが、<br>
- 調査する範囲が担当者によって異なる
- 情報のまとめ方が人によってばらつく<br>
といった課題があり、原因特定のスピードや精度に差が出ると感じました。<br>
また、アプリケーションチームが利用しているサーバーで障害が発生した場合、
インフラチームによる調査を待つ必要があり、　
- 調査開始までに時間がかかる可能性がある
- 初動対応が遅れるリスクがある<br>
という運用上の課題もあると考えました。<br>
これらの背景から、ログ・メトリクス・操作履歴を統合し、AIによって原因分析を自動化することで、<br>
「調査の属人化解消」と「初動対応の迅速化」を目的として本システムを構築しました。

# 使用サービス
- Amazon EC2
- Amazon CloudWatch Logs
- Amazon CloudWatch Metrics
- Amazon CloudWatch Alarm
- AWS CloudTrail
- AWS Lambda
- Amazon Bedrock（Claude）

# サービス選定理由
サービス：選定理由
Amazon EC2：監視対象となるWebサーバーを再現するため
CloudWatch Logs：nginxのアクセスログ・エラーログを一元管理するため
CloudWatch Metrics：CPU使用率を監視し、高負荷状態を検知するため
CloudWatch Alarm：閾値超過を契機にLambdaを自動実行するため
AWS Lambda：サーバー管理不要で、イベント発生時のみ処理を実行できるため
AWS CloudTrail：障害原因となり得る設定変更や操作履歴を確認するため
Amazon Bedrock：AWS内で生成AIを利用し、監視情報を自然言語で分析するため

# 処理フロー

1. EC2でアプリケーションが動作<br>
2. CloudWatch Logsにログが蓄積される<br>
3. CloudWatch MetricsでCPUなどのメトリクスを取得<br>
4. CloudWatch Alarmが閾値超過を検知<br>
5. Lambdaが自動起動<br>
6. Lambdaが以下の情報を取得<br>
   - ログ（CloudWatch Logs）
   - CPU使用率（CloudWatch Metrics）
   - 操作履歴（CloudTrail）<br>
7. Lambda内でデータを整形<br>
8. AIに渡すため自然言語へ変換<br>
9. Bedrock（Claude）で原因分析<br>
10. 分析結果をCloudWatch Logsに出力

# 本システムの前提・制約
- 現在は単一のEC2インスタンスを監視対象としています。
- 異常検知条件はCPU使用率70%以上としています。
- CloudWatch Logsから取得するログは最新5件に限定しています。
- Amazon Bedrockの分析結果は初動調査を支援するものであり、最終判断は運用担当者が行う想定です。
- 本システムは原因分析までを対象とし、自動復旧や通知機能は未実装です。

# 工夫した点
- CloudWatch Logs・CloudWatch Metrics・CloudTrailの3種類の情報を統合してAIへ渡すことで、ログだけでは判断できないシステム全体の状況を分析できるようにしました。
- CloudWatch AlarmをトリガーとしてLambdaを自動実行する構成とし、異常検知からAI分析開始までを自動化しました。
- AIへデータをそのまま渡すのではなく、ログ・メトリクス・操作履歴を自然言語に整形してからAmazon Bedrockへ送信することで、分析結果が分かりやすくなるよう工夫しました。
- 正常時の動作確認だけでなく、EC2へCPU負荷を発生させる異常系テストを実施し、CloudWatch Alarm・Lambda・Amazon Bedrockが連携して動作することを確認しました。

# 構築時に発生した問題と対応
| 問題 | 原因 | 対応 |
| CloudWatch LogsでSignature expiredが発生 | PCの時刻ずれ | OSの日時設定を修正 |
| Claude Sonnet 5を呼び出せない | AWSアカウントで利用不可 | 利用可能なClaude Sonnet 4.5へ変更 |
| Bedrock呼び出しでMalformed input request | 文字列で組み立てたJSONが不正 | Python辞書を`json.dumps()`で変換 |
| Lambdaが3秒で終了 | デフォルトタイムアウトが短い | タイムアウトを30秒へ変更 |
| AlarmからLambdaを起動できない | Lambdaのリソースベースポリシー不足 | `lambda:InvokeFunction`権限を追加 |

# セキュリティ上の考慮
検証を優先し、構築時はAWS管理ポリシーを使用しました。<br>
本番運用を想定する場合は、Lambdaが参照するロググループ、EC2メトリクス、CloudTrailイベント、Bedrockモデルに対象を限定したカスタムIAMポリシーへ変更し、最小権限の原則を適用します。

# コスト面の考慮
- EC2は検証時のみ起動し、未使用時は停止しています。
- Lambdaはイベント駆動とし、常時稼働するサーバーを追加していません。
- CloudWatch Logsの保持期間は30日に設定しています。
- Bedrockは推論実行時のみ課金されるため、必要なタイミングに限定して呼び出します。

# 今後の改善
